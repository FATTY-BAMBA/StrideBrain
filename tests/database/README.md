# Database tests

Use Node 24 and set `DATABASE_URL` to a disposable local PostgreSQL server connection, with a role allowed to create databases. Run `npm run check` (or `npm run test`). The named database is only the administration connection: setup never migrates, seeds or drops it. Tests without a DATABASE_URL retain the previous unit-only behavior; full verification always supplies it and requires zero skipped tests.

The global setup applies every committed migration's SQL in order to one fresh `sb_test_<run>_template`. It reads the seed and verification script order from package.json, executes both twice, then closes the template connection. Each fork worker gets `sb_test_<run>_worker_<pool id>`, cloned from that template before **every file**, including after a file fails. Hook order is stack: file cleanup finishes before the shared Prisma disconnect. Global teardown removes only this run's prefixed databases, including temporary snapshots.

CI also exercises the real deployment commands against the PostgreSQL service's base database before `npm run check`: `npm run db:migrate`, `npm run db:seed`, `npm run db:verify`, then `npm run db:seed && npm run db:verify` again. These steps cover `prisma migrate deploy`, `prisma db execute` and repeatable seeding through the actual CLI. The test setup applies SQL files itself, so its isolated template lifecycle does not replace that deployment-command coverage. Only those explicit CI steps migrate and seed the base database; the test setup still uses it solely as an administration connection.

A migration test that needs an older schema calls `resetWorkerDatabase(true)` before opening clients, then applies its original migrations and fixtures. Do not create a separate ad-hoc database. Most suites simply use `process.env.DATABASE_URL`; the test file must close its own pg/Prisma clients. Never capture a client before per-file setup or depend on another file's writes.

`assistantDatabase` uses the managed worker for ordinary tests. For its nested synthetic scenarios, run-owned snapshots preserve/restore the worker's previous state; application queries still use the same worker database. The paid evaluation config clears these ordinary-suite hooks and retains its separate existing fixture lifecycle. No paid provider is called by these tests.

Only localhost, 127.0.0.1, IPv6 loopback, and the `postgres` service name with CI=true are accepted. Connection-routing URL parameters and names outside the current run prefix are refused before database mutations. Never point tests at hosted projects. The negative-control configs under `probes/` deliberately share/retain a run-owned database only to prove the guard assertions fail; they are not switches in the ordinary setup.

`npm run test:stability` requires committed implementation files and runs `npm run test` 20 independent times, stopping at the first failure. The first ten use normal file ordering; the next ten shuffle **files only** with seeds 71001–71010, preserving existing within-file test scenarios. It records counts, the unchanged hero-test hash, commit, timing and one log per run. It is evidence collection, not retries. Never reduce counts, skip tests or weaken assertions to make it pass.

`tests/quote-comparison/http-postgres.test.ts` starts a real local Next development server on an ephemeral loopback port against that file's isolated worker database. It issues synthetic sessions through the existing session service, sends HTTP requests to both private quote routes, verifies Run/Refresh persistence and audit, checks that GET does not write, and verifies Viewer/anonymous denial. The server receives only an explicit local environment (AI disabled), is stopped before the database is removed, and makes no hosted request. This complements direct route tests: a Node HTTP POST reaches Next with a body stream even when it carries zero bytes. The test fails against the old truthy-body check. Run it with the ordinary full suite; no separate CI opt-in is required.
