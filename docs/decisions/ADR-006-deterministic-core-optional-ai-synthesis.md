# ADR-006 — Deterministic Core with Optional Verified AI Synthesis

**Status:** Proposed for Technical Architecture acceptance  
**Date:** 2026-11-14  
**Decision owners:** Product Director, Technical Architecture, Intelligence Evaluation, Security Review  
**Applies to:** Comparable Project Intelligence v0.1

## Context

StrideBrain should feel conversational and intelligent, but the first workflow influences commercial review.

Eligibility, similarity scores, quotation/actual-cost distinctions, financial calculations, evidence, and action authority cannot depend on non-deterministic model judgment.

The old prototype proved useful patterns for bounded read-only model tools and citation verification. The customer-facing product can preserve those safety lessons without making the model the source of business truth.

## Decision

The v0.1 workflow has two independent layers:

### Required deterministic core

Produces:

- active project context;
- candidate eligibility;
- `CPI-SIM-1.0` factors/scores/ranking;
- historical economics under `EVIDENCE-AUTHORITY-1.0`;
- sufficiency/conflict/stale decisions;
- claim-level evidence;
- structured synthesis;
- ProposedAction fields/requirements.

This layer is the authoritative product result.

### Optional AI synthesis

May produce:

- concise natural-language explanation of the verified result;
- localized narrative framing;
- a draft action title/rationale from supplied structured claims;
- follow-up question suggestions grounded in available result actions.

It is secondary and may be disabled.

## Model input boundary

The model receives only:

- authorized role-specific ComparisonResult data;
- verified StructuredClaims;
- evidence labels/IDs already accessible to the user;
- explicit locale/style instructions;
- bounded recent conversation context when needed.

The model does not receive unrestricted repository access or broader tenant data.

## Model prohibitions

The model may not:

- add/remove candidates;
- alter rank, factors, weights, scores, or bands;
- calculate authoritative financial values;
- relabel quoted/forecast/offer/actual authority;
- resolve conflicts or refresh stale evidence;
- produce an actual-cost range after insufficiency;
- infer inaccessible records;
- create Action state;
- approve/issue quotes;
- contact anyone;
- claim success before service receipt.

## Verification

Model output is checked against the supplied result/claim ledger.

Verification rejects or removes:

- unknown IDs;
- unsupported amounts/percentages;
- authority-type conflation;
- claims contradicting insufficiency/conflict/stale states;
- unsupported causation;
- action-execution claims;
- citations outside the authorized set.

One bounded repair attempt may be allowed. If still invalid, the optional explanation fails and the structured result remains.

## UX behavior

- structured result renders first;
- optional explanation has a separate loading/failure state;
- explanation cannot reorder cards or modify table values;
- user can complete evidence inspection and action flow without it;
- provider/model identity is not normal business UI;
- no fake sample answer is shown as live synthesis.

## Service interface

```ts
interface OptionalExplanationService {
  explain(
    ctx: RuntimeContext,
    input: AuthorizedComparisonExplanationInput
  ): Promise<
    | { kind: "SUCCESS"; explanation: VerifiedExplanation }
    | { kind: "UNAVAILABLE"; code: string }
  >;
}
```

The service has no business-write method.

## Action rationale

A model-assisted rationale is treated as editable proposal text.

Mandatory verified lines/warnings are generated by deterministic code and cannot be removed silently.

The server uses the structured proposal/evidence, not the model prose alone, when authorizing Action creation.

## Model routing

Provider/model selection is an infrastructure/admin concern.

Normal v0.1 users see `StrideBrain`, not a public model selector.

Any model allowlist, budget, timeout, or fallback behavior lives server-side and is observable.

## Consequences

### Positive

- product remains useful without AI provider availability;
- commercial facts are reproducible/testable;
- hallucinated scores/values cannot become authoritative;
- model innovation can improve language without changing core logic;
- safer bilingual explanation;
- clear eval boundary.

### Costs

- deterministic services/schema are more work than prompt-only implementation;
- output verification is required;
- optional explanation may fail rather than return fluent unsupported text;
- providers/models cannot freely redesign the response.

These costs are accepted because evidence-backed trust is the product differentiator.

## Rejected alternatives

### Model decides candidate ranking

Rejected as opaque/non-reproducible and difficult to secure/evaluate.

### Model directly queries all tenant repositories

Rejected for v0.1 because it broadens permissions/tool risk and is unnecessary for the bounded slice.

### Chat-only product result

Rejected because it obscures structured factors, authority, evidence, and actions.

### AI required before showing any result

Rejected because provider latency/failure would block otherwise deterministic intelligence.

### Static scripted answer fallback

Rejected as a substitute for intelligence. The fallback is the verified structured result, not a fabricated conversation.

## Required evaluations

- structured result unchanged across model providers/failures;
- unsupported IDs/amounts rejected;
- quote/actual conflation rejected;
- lighting insufficiency preserved;
- schedule causation not invented;
- citations limited to supplied authorized evidence;
- zh-TW and English explanations faithful;
- model cannot create state;
- explanation timeout does not block hero flow/performance budget.

## Rollback implication

The optional explanation feature can be disabled through configuration/feature flag without affecting comparison, evidence, or action creation.

## Acceptance criteria

- deterministic core alone satisfies the complete product flow;
- model input is authorized/redacted/bounded;
- output verified against structured claims;
- model cannot change business state or authority;
- provider failure has a designed minor state;
- provider/model details remain out of normal UX;
- tests prove structured and action results are independent of AI availability.
